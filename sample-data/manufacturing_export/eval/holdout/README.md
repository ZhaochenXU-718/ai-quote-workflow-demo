# Holdout Evaluation Set (hand-written)

This is a small, **hand-written** evaluation set whose gold labels were derived
by reading each email and deciding what a *correct* system should output. It is
deliberately **not** produced by `scripts/generate_manufacturing_export_data.py`.

## Why it exists

The default dev set (`inquiries/synthetic_inquiries.jsonl` +
`eval/gold_answers.jsonl`) is generated by the same logic the rule pipeline
implements. So its 100% pass rate only proves the pipeline reproduces its own
synthetic data — it cannot tell us whether the system *generalizes* to phrasings
it has never seen.

This holdout breaks that circularity:

- Every inquiry uses phrasing the generator never emits (synonyms, units instead
  of `pcs`, sizes in inches, delivery in weeks, quoted email threads, non-English
  emails in German/Spanish/French/Arabic, application phrased outside the
  `for a X in {country}` template, etc.).
- Gold is human truth, written independently of the pipeline.
- It is **expected to score below the dev set**. That gap is the signal. A low
  score here is a feature: it shows where the regex baseline breaks and gives
  P5 (LLM) something real to improve against.

All rows are still `synthetic: true` — these are invented emails, not real
customer data.

## How to run

```bash
python3 -m backend.app.cli p0 --holdout      # validate the holdout contract
python3 -m backend.app.cli eval --holdout    # score the pipeline on the holdout
python3 -m backend.app.cli run INQ-HOLD-001 --holdout   # inspect one case
```

Note: `eval --holdout` exits non-zero while cases fail. That is expected — the
holdout is a **diagnostic**, not a regression gate. The regression gate is the
default `eval` (which must stay green). Do **not** tune the pipeline to make the
holdout pass; that would just re-introduce overfitting. Instead, re-run it after
each capability change (P3 retrieval, P5 LLM) and compare the trend.

## Probe map

Each case targets a specific, known weakness of the P1 regex baseline.

| inquiry_id | Probe | Expected baseline failure |
|---|---|---|
| INQ-HOLD-001 | quantity as "300 units" (not `pcs`) | quantity not extracted |
| INQ-HOLD-002 | size "2 inch" (= DN50) | size missed → false missing-spec + false "size" missing field |
| INQ-HOLD-003 | "SS ball valves" abbreviation | product not recognized → no candidates, cascade |
| INQ-HOLD-004 | delivery "three weeks" (= 21 days) | delivery not extracted → delivery risk missed |
| INQ-HOLD-005 | quoted thread mentions other valves | wrong product picked from quoted noise |
| INQ-HOLD-006 | two products joined by "and" | multi-product not detected; field bleed across line items |
| INQ-HOLD-007 | material "316L stainless steel" | material missed → false missing-spec |
| INQ-HOLD-008 | application outside `for a X in {country}` | false-fires `unclear_application` (precision probe) |
| INQ-HOLD-009 | German-language email | near-total failure (multilingual gap) |
| INQ-HOLD-010 | "five hundred" + "DN 50" with a space | quantity and size missed |
| INQ-HOLD-011 | control: near-template phrasing | expected to PASS |
| INQ-HOLD-012 | "S/S ball valves" + "Qty 80" | "flanged" substring hijacks product to a flange |
| INQ-HOLD-013 | size "1.5 inch" + UL cert not supported | size missed; cert risk still caught |
| INQ-HOLD-014 | Spanish-language email | near-total failure (multilingual gap) |
| INQ-HOLD-015 | French-language email | near-total failure (multilingual gap) |
| INQ-HOLD-016 | Arabic-language email (RTL) | near-total failure (multilingual gap) |
| INQ-HOLD-017 | English email demanding a guarantee | `restricted_claim` fires correctly → expected to PASS |

The `probe` field on each inquiry line records the same intent inline.

INQ-HOLD-017 is a positive test for the now-live `restricted_claim` rail: a
correct, in-English inquiry that simply demands a guarantee, which the baseline
*should* flag. It is expected to pass, confirming the rule integrates without
breaking a clean case.

Recorded so future changes can be compared against it:

```text
total_inquiries: 17
passed: 2            (control INQ-HOLD-011 + restricted_claim positive INQ-HOLD-017)
pass_rate: 0.1176
field_accuracy: 0.8235
product_candidate_precision: 0.6667   recall: 0.5556   f1: 0.6061
risk_flag_precision: 0.6047   recall: 0.8387   f1: 0.7027   (12 inquiries with false positives)
missing_field_precision: 0.4167   recall: 1.0   f1: 0.5883   (7 inquiries with false positives)
```

Contrast with the default dev set, which scores 1.0 across the board — the
difference between those two numbers is the honest measure of where the system
stands today.
